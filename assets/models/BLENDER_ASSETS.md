# Blender energy equipment assets

Created and exported with Blender 4.3.2, using `build_assets.py`. These are actual editable meshes and self-contained glTF 2.0 binary assets, not concept art. The paired PNGs are Cycles renders of the same meshes.

## Files in this game

- `wind_turbine.glb`, `solar_array.glb`: deployed meshes
- `solar_array_PV_cell_atlas_256.png`: generated by Godot while importing the embedded atlas
- The source `.blend` files, build script, previews and exporter-validation scripts are in the separately supplied Blender asset source bundle, not this runtime folder.

The .blend files include a studio floor, lights and camera for reproducible previews. These were added **after** GLB export and are absent from the GLBs. To re-export manually, select only the equipment root and descendants, and enable Selected Objects. Do not export the studio.

## Coordinate and scale contract

Both GLBs are Godot Y-up, grounded at y=0 with root position/rotation zero and scale one. Blender source uses Z-up; standard glTF Y-up export converts axes. No additional 90-degree rotation is needed in Godot.

Wind uses 0.1 world units per meter: 90 m hub height = y 9; 126 m nominal rotor diameter = 12.6 world units. Its asymmetric swept blade tips extend about 0.003 units beyond nominal radius. The rotor faces -Z. The static, initial-pose AABB is x [-5.367,5.557], y [0,15.300], z [-1.500,1.200]. Reserve a rotational footprint radius of at least 7.

PV is deliberately a compressed field representation, not a scale model of 16,000 m² of panels. Twelve panel faces are 1.55 × 1.7 world units each; nominal fixed tilt is 25 degrees. Field AABB is x [-3.500,4.225], y [0,1.242], z [-3.300,3.300]. Reserve radius 5. Panel face normals point toward +Z with upward component. The preview camera views from that side to show the cells.

## Nodes and animation

WindTurbine
- Structure (merged static mesh, six material surfaces)
- Rotor (Node3D, translation 0,9,-0.89)
  - Blade_1, Blade_2, Blade_3 (individual airfoil meshes)
  - Spinner
- ElectricityPort (Node3D, translation 1.15,0.65,-0.37)

SolarArray
- ArrayAssembly (merged static mesh)
- ElectricityPort (Node3D, translation 3.75,0.38,-0.30)

Find `Rotor` recursively after instantiation. Animate its **local Z rotation**, e.g. rotor.rotation.z += radians_per_second * delta. Do not rotate the entire root. The asset has no baked animation or autonomous gameplay script.

## Integration

Wrap each imported scene in the existing EquipmentNode so the existing preview, selection, port and simulation APIs remain authoritative. Recursively gather MeshInstance3D nodes for placement tint. Their materials live on mesh surfaces; `material_override` initially is null. Restore null after preview instead of replacing the six surface materials with a single material. Keep selection ring and terminal overlays in game code.

The GLBs are fixed-design visuals. Keep the procedural path for profile-dependent hub height, rotor diameter or PV tilt until a deliberately parameterized Blender variant system exists. The assets must not add capacity, electrical connections, or model devices. Preserve the existing physical model as the single source of truth. Static components have been merged for fewer draw calls, so procedural test names such as Tower or Panel_r_c are not preserved as visible mesh nodes.

## Performance and materials

- Wind: 2,796 triangles, 5 mesh objects, 6 PBR materials; approximately 148 KB GLB.
- PV: 9,528 triangles, 1 mesh object, 6 PBR materials; approximately 665 KB GLB.
- Only texture: an embedded 256×256 generated PV cell atlas. No remote textures, external files, transparency, custom shaders or extensions required for core appearance.
- Solid PBR materials use base color, metallic and roughness. Materials are muted ceramic white, marine blue, galvanized metal, concrete, dark backsheet/vents and aggregate.

2. Both rendered previews inspected for proportion, grounding and silhouette. PV UVs mapped over full panel faces; support tilt and frame alignment inspected.

Rebuild: `blender -b -t 6 --python build_assets.py`.

## Implemented game adapter

`EquipmentVisual.create(kind, params, prefer_blender_assets=false)` preserves the existing two-argument procedural API. The controller may pass `true` to use these assets for reference geometry. Wind hub height other than 90 m or rotor diameter other than 126 m, and PV module area other than 16,000 m² or tilt other than 25°, explicitly fall back to the parameterized procedural model. Electrical-only edits do not change geometry selection. `visual_backend`, `asset_source` and `asset_fallback` metadata make the active path inspectable.

The wrapper recursively registers imported mesh surfaces, restores their original null material overrides after placement preview, animates the imported Rotor around local Z, and uses the exported ElectricityPort position for the standard game terminal. Load, battery and station retain their independent procedural models.

Main-project headless integration test: `godot --headless --path . --script tests/test_blender_equipment.gd`. It checks both imported assets, actual-vertex grounding and siting bounds, preview restoration, rotor movement, electrical port transforms and geometry fallback. Native camera/terrain visibility and visual performance still need runtime QA.
