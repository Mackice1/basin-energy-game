# GLPK 电储能边界事务的可表示数值修复

公开整理说明：本文保留研究或开发阶段记录；带时间的计数、计划与待验收状态仅适用于对应时点，不代表逐项人工验收已完成。最终范围见[最终原生验收](FINAL_NATIVE_ACCEPTANCE_1004.md)。原始运行日志、截图、玩家存档、备份与研究图像不随源码分发；下文非公开记录仅为来源说明。公开整理没有重新运行游戏或测试。

日期：2026-10-21。生产修改仅 `tools/dispatch_solver.py`；没有修改 Godot 库存边界、物理方程、几何 guard、运行参数、用户存档或求解目标。没有 GUI 操作。

## 根因

两份非公开求解记录（未随源码分发）保留原失败结果。原两步充放方案末库存为 -1.11022302462516e-16 MWh。GLPK 的库存、端口与路径是独立决策，解文件又作十进制有限精度输出；它们仅在浮点容差内一致。原 `assemble_schedule` 直接发布解的库存，而 Python 边界审计允许数值容差，Godot 对落盘/应用库存的严格非负检查正确拒绝。

这不是只把负零写成零的问题。默认 LAES 的实际衰减后库存约 0.6153846153846148 MWh，按路径输出 0.4 MW、放电效率 0.65、步长 1 h，真实递推也略小于零。单改库存会掩盖超提。

## 修复边界

新增 `realize_electric_storage_transactions`，位置在原始 GLPK 模型行与独立物理双审计通过之后，最终报告组装之前：

1. 按真实路径顺序和原线路/站损耗重算电储能实际充入、放出；从初始库存逐步递推，不信任孤立的 energy 决策。
2. 只有触空/满仓的机器数值残差可以修复。采用与实际历史事务量级相关的 ULP 预算，电量与功率分别检查，没有统一绝对 MWh 夹断阈值。历史量级须延续到之后的零需求/近空步，否则真正保留下来的极小余额会被错误当作不一致。
3. 通过 `math.nextafter(..., 0)` 保守减少真实路径流率，绝不增加路径或补充能量。微超提减少储能到负荷的实际供电，并相应增加未供；微过充减少发电到储能的实际输送，并相应增加弃电。
4. 全部端口、状态、线路、节点、损耗与汇总从修正后的决策重新组装。库存就是递推表达式的结果，不作 `max(energy, 0)` 或容量截断。
5. 超出能量/功率 ULP 预算，或触边事务涉及不能独立闭合的耦合辅机时明确失败；不单独改辅机供电而保持其产物/热量。不改二元模式或物理系数。
6. 再次审计模型行、原目标锁和独立物理账；Godot 仍使用原严格审计。大偏差和伪造库存继续拒绝。

`storage_transaction_normalization` 披露方法、路径/端口/库存决策修改数、最大路径 MW 调整、预算规则、没有夹库存/补电，以及并非未经变化的原 LP 决策。`objective.published_schedule_values` 保存实际发布方案重新计算的全部目标；原 solver stages 保留原始求解证据。最优标记仍基于 GLPK 求解完成与既有目标锁审计容差，不宣称二进制下逐位等同原 LP 解。

## 原失败样例的实际修正

- 默认 LAES：最大路径减少约 3.3306690738754696e-16 MW；最终库存 1.1102230246251565e-16 MWh。
- 半容量、放电效率 1：最大路径减少约 2.7755575615628914e-16 MW；最终库存 5.551115123125783e-17 MWh。

这些正微量余额来自更少的真实放出，并继续衰减/延续，不被截为零，也不在末步隐藏。

## 专项与交叉验证

`tests/test_storage_transaction_realization.py`：3 个测试方法，包含：

- 原两 fixture、带/不带新几何标识、两步/追加第三步零需求，共 8 组；相同输入重复求解，报告、汇总、库存与修正 metadata 确定性一致。
- 固定种子 20261021 的 36 组随机分数步长、不同效率/容量/自耗、满仓充电、多步耗尽、末步延续，部分含线路与站损耗。
- 44 组均使用真实 GLPK，逐步严格检查 `0 <= energy <= capacity` 及库存恰等于实际递推，随后由原 Godot 入口独立复审；每例再伪造 -1e-16 库存，必须被 Godot 拒绝。
- 对原始解确认所有改动路径只减少、未供相应增加、目标重算；大库存/路径偏差和不可闭合辅机路径拒绝，原输入与原决策字典不变。

原空气专项、扩展储能、基础电网、CO₂、燃料、热水、Rankine、塔式、物料、相变氢与化工 Python 套件另外用真实 GLPK 复跑；最终日志见同目录证据。早期部分旧套件只读取 PATH 而不读取 BASIN_GLPK，曾跳过其集成项；随后已把真实 glpsol 加入 PATH 后重跑，不能将早期跳过算成通过。
